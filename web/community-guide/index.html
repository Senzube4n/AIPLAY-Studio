01 / Windows setup

Install Studio, then choose the engine.

Use the official Windows Setup 1.5 release and its AIPLAY Studio Setup.exe. This installs the app and a private Node.js runtime when needed; it does not install every AI model.

  1. Run Setup, choose Senzu's build and the intended folder, then open the AIPLAY Studio shortcut.
  2. Choose Music only for the Windows native YuE2 GGUF path, or Full Studio for pictures, video, DAW and Production.
  3. Keep the launcher running. In Models, review the feature's size, terms and prerequisites, then install it deliberately.
Launcher modeFirst useSeparate requirements
Music onlyWindows native YuE2 GGUF songsAutomatic runtime targets Windows x64: CUDA on NVIDIA, Vulkan on AMD/Intel, CPU without a GPU. Model/runtime downloads are separate.
Full StudioCreative suite and DAWLocal AI tools need a compatible engine, dependencies and model files. App installation is not a model benchmark.
Use Comfy APIOptional hosted modelsYour Comfy key and credits. This mode has no Music, Production or Collab screens.

If a fresh install says a shared module is missing: close Studio, download the newest Setup and install into the same folder. Old Setup 1.2 could omit shared/worker even when the displayed app build was current. Setup 1.4+ checks required files and startup imports before replacing the app. Reinstalling Python or redownloading models is not that repair.

If antivirus blocks Setup

Setup is unsigned. Keep a detected file quarantined, retain its detection name and SHA256, and report it for review. Setup 1.5 removed self-delete-on-close and uses locked npm installation without lifecycle scripts; these changes do not establish antivirus approval. Use the public source without running either Studio executable:

npm.cmd ci --omit=dev --ignore-scripts
node launcher/launcher.mjs

First install Node.js 20+ if absent, extract the official source ZIP into a new folder and run those commands there. Existing user settings/model paths are reused; custom workflows in an old app folder must be copied separately. If another detection occurs, report that exact command/message rather than assuming it is harmless.

Windows Battery Safe is opt-in. The PowerShell battery reader stays off until you explicitly enable Settings → Battery Safe → stop on battery. Old saved defaults do not opt in. Turning it off stops that reader; other Windows helpers are separate. Enabling it can still trigger a security product's PowerShell detection.

Start small. Native Q4 model files total about 2.93 GB; optional Q8 about 4.53 GB, plus the separate runtime. Higher precision is not a certified sound-quality or speed improvement; disk size is not a VRAM requirement.

Source installation on another platform

Install compatible Node.js 20+, extract the official source ZIP, then run npm ci --omit=dev --ignore-scripts and node launcher/launcher.mjs. Source installation still does not create a compatible AI engine. The Linux/Mac desktop packages below already supply Node/npm for the app.

Checkpoint: the app opens and Models gives an honest readiness result for your chosen feature.

02 / Linux

Install from the application menu.

Choose your processor: Intel/AMD 64-bit .deb or ARM64 .deb. These target Ubuntu 22.04/24.04 x64 and Ubuntu 24.04 ARM64. Other Debian-based systems need their own testing.

  1. Open the .deb in your software installer and press Install. Your distribution may request your account password.
  2. Open AIPLAY Studio from the application menu. A browser setup page downloads Studio and opens its launcher. First setup needs GitHub/npm internet access; no manual Node/npm/Git/Python installation is needed for the app itself.
  3. Choose the mode you need. Connect a compatible local engine or configure a supported remote/hosted route; select model downloads separately.
  4. For later app updates, stop Studio and use the launcher's Update. A newer package updates the bootstrap/private runtime.

App support is not engine parity. The automatic native YuE2 GGUF runtime installer remains Windows x64 only. Linux needs a compatible ComfyUI music workflow or your own compatible native CLI. Local H3/MOSS and other models still need supported dependencies, hardware, memory and applicable model terms.

Portable bundle, repair and user files

For another supported glibc-based distribution, get the matching .tar.gz from the Linux release, extract it to a permanent folder and run aiplay-studio. It needs tar, CA certificates, xdg-open and a working browser. These Node binaries do not support Alpine/musl.

Close Studio before aiplay-studio --repair. Do not run the app with sudo. Removing the package keeps the app under ~/.local/share/aiplay-studio/, settings under ~/.aiplay-studio/ and configured model/output folders. Review user files before deleting anything else; preserve an unfamiliar or live setup lock.

03 / macOS developer preview

Drag the matching app to Applications.

In Apple menu → About This Mac, check the chip. Download Apple silicon ARM64 for M-series Macs, or Intel x64. Declared minimum: macOS 13.5. Actual native acceptance covered Apple silicon on macOS 14/26 and Intel on macOS 15.

  1. Open the .dmg and drag AIPLAY Studio into Applications.
  2. Eject the disk image. Open the copied AIPLAY Studio.app in Finder.
  3. The browser setup page downloads Studio and opens its launcher. Private Node/npm are included; first setup needs GitHub/npm internet access. Opening setup does not download an AI model.
  4. Open the running app again in Finder to reopen the browser page through the same native host. Stop Studio before using the launcher's Update.

Ad-hoc-signed developer preview: no Apple Developer ID signature or notarization. macOS may block a downloaded copy; native CI does not establish Gatekeeper approval. Keep protections enabled and report the exact message if it refuses to open.

Studio, the launcher and DAW were tested separately from AI inference. The Windows native YuE2 automatic installer does not run on a Mac; local YuE2, H3 or MOSS generation is not promised by app startup. Use each engine's live readiness and compatible dependencies, or a supported remote/hosted route.

Repair, checksums and removal

With Studio closed, run "/Applications/AIPLAY Studio.app/Contents/MacOS/AIPLAY Studio" --repair, adjusting the path if needed. Setup stages and validates replacement files while preserving user settings/custom workflows. Compare the DMG with SHA256SUMS.txt from the same release using shasum -a 256 path/to/download.dmg; a matching hash is not notarization.

Trashing the app bundle removes its bootstrap/private runtime but keeps the writable app under ~/Library/Application Support/AIPLAY Studio/, settings under ~/.aiplay-studio/ and configured models/output. It does not replace system Node or another app's Python.

04 / Music

Make a song, then keep its recipe.

Platform scope: the native GGUF quickstart uses its Windows x64 automatic runtime. Linux/macOS need a separately compatible music engine. Open Music. A new installation starts in Simple: choose Presets… or describe a song, review the draft and press Make song. For direct control, use Song or Advanced as offered by your build; the label and layout vary. Select the ready YuE2 engine, enter Style and Lyrics, and press Create.

For the native GGUF path, both style and nonempty lyrics are required. Put section tags such as [Verse], [Chorus] and [Bridge] on their own lines. Be concrete about instruments, vocal delivery and arrangement. An instrumental checkbox, recording reference, tempo field or LoRA picker from another engine should never be assumed to work on this route.

A useful style brief

Describe the musical roles: “Warm synthpop, restrained lead vocal, rounded bass, sparse verses, brighter layered chorus, a short instrumental bridge and a clear ending.”

A descriptive prompt is an experiment. Listen for what the model actually follows.

A useful comparison

Make two or three takes. Keep the words and style fixed while the seed changes. Compare the opening, chorus, intelligibility and ending before choosing.

Change one meaningful thing on the next round and record why.

  1. Wait for the queued job to finish. The completed recording appears in the Library; native output is WAV.
  2. Listen to the entire take. A file can complete successfully and still omit a lyric, lose a section or end early. A Check ending warning means the ending needs attention; no warning is a musical guarantee.
  3. Keep the exact engine, model, lyrics, style, seed and settings with your favourite. The same seed does not promise identical sound across runtime versions or different hardware.
  4. Use Music's Takes for queued performances of one idea. Use Batch & schedule for multiple different ideas; Studio must stay running and the computer awake.

Know which YuE2 you selected. Native GGUF, Python YuE2 and YuE2 through ComfyUI have different controls, runtime needs and saved artifacts. Native GGUF has no direct singer-reference or waveform-continuation input. A new longer arrangement is a new performance; it is not guaranteed seamless extension of your existing recording.

Study exercise: share a short owned example and the one recipe change you tested. Tell the group what improved and what did not.

05 / Pictures

Build a small visual world.

In Full Studio, open Pictures. Choose an installed engine, write one clear prompt, choose a size that your setup supports, and press Make image. Start with a single composition before expanding into a cast or a scene list.

For a cover or visual concept, describe the subject, framing, environment, light and colour. Add exact title text later in the editor when accuracy matters. If the engine supports references, use Reference images → Upload… (or Use a file… in another layout) or an image from the library. An engine without reference support cannot be made consistent just by adding an attachment.

  1. Make or import one useful reference for the subject. Prefer a clear single panel over a crowded contact sheet when identity matters.
  2. Try the same subject in a second setting. Check face, silhouette, wardrobe and accessories. A reference can also carry unwanted pose or background.
  3. Keep the strongest image. Use the image editor's layers, selections, cutout, colour adjustments and text for ordinary finishing.
  4. Save the prompt and chosen reference files. Keep credits and required model/source notices with the project.

Read the selected model's terms. AIPLAY's application licence is not the licence for every model, adapter or reference image. The Models screen shows feature-specific notices. For Qwen Image 2.1, a missing-node message can offer Fix Qwen; engine support and the model download are separate checks.

Study exercise: make one subject readable in two different environments, then show where consistency still breaks.

06 / MOSS recipes

Try the faster recipes deliberately.

MOSS is an optional text-to-image engine. Qwen Image 2.1 remains the automatic picture choice and the reference/editing route. Installing MOSS does not switch your saved default, update ComfyUI or replace a patched engine. An unavailable readiness result is a setup issue to resolve before rendering.

  1. In Models, install MOSS-Image SFT (experimental): its checkpoint, GPTQ encoder and small VAE total about 13.01 GB on disk.
  2. Open Pictures → Advanced. Choose engine MOSS-Image (experimental, text only), then preset Standard.
  3. Use 1024 × 1024, how many: 1, a clear prompt and a recorded seed. Click check; get files opens missing-model offers. Wait for ready, then Make image.
  4. Keep the baseline picture/recipe. Install only the addition you want, choose its preset and repeat the same prompt, seed and size where permitted.
  5. Inspect composition, text, hands, faces and style. Separate first-load from resident-model timings.

All use native shift 5, raw prompts and no skip-layer guidance. Non-Standard presets fix their recipe controls. CFG-1 recipes refuse negative prompts. Standard/Spectrum/Kromoss Standard allow multiples of 16, 256–2048 per side and count 1–4. Accelerated adapter presets cap either side at 1536 pixels. These input limits are not memory guarantees.

Install the matching addition

Models names the experimental additions MOSS-Image Turbo 4, MOSS-Image DMD 8, Kromoss INT8, Kromoss DMD2 8 and MOSS HiRes v0.3. Kromoss is a full fine-tune, not a small SFT adapter; it reuses the shared encoder/VAE. Its DMD2 file is distinct from SFT DMD. Do not download whole publisher repositories or rename files to imitate another model.

Spectrum adds source code, not weights. Use the pinned standalone setup instructions linked beside an unavailable Spectrum preset. Install into the intended compatible engine, verify the pack, then restart only while its jobs are idle. Copying files alone does not reload a running engine.

HiRes makes a new picture

Choosing MOSS HiRes (4 MP) sets the fixed 2048-square canvas and one image; leaving restores the earlier size/count. This is direct generation, not an upscaler. It uses native VAE decoding without a silent tiled fallback. Its reviewed release supplies no explicit adapter licence, so Models records unknown terms.

Optional Uncensored preset, with a neutral exercise

Install MOSS NSFW Uncensored (optional), then choose NSFW Uncensored. The 74.4 MB model-only adapter uses strength 0.7 and CLIP strength 0. Begin the prompt with moss_xvstyle; Studio does not insert it. A fully clothed adult portrait is enough to learn the controls. No explicit imagery is needed for this exercise.

The adapter publisher supplies Apache-2.0; reference/output rights are separate. Publisher example content and quality have not been validated. Studio's native INT8 requantization differs from its BF16 example. This is an explicit optional recipe, not a global default or a guarantee about output.

Measured examples, not a universal ranking: RTX 4070 Ti SUPER 16 GB, ComfyUI 0.42.1/PyTorch 2.14.1, two new resident-model prompts at 1024² averaged Standard 16.920 s, H1 12.375 s, H2 11.928 s, Turbo 4 4.988 s and DMD 8 6.138 s. These are Studio job durations for different recipes. Turbo's portrait was softer and framing changed. Kromoss/HiRes/Uncensored do not inherit those results.

Use Qwen for references and edits. Shipped MOSS recipes refuse image references, personas, editing, transparency, arbitrary adapter stacks and CLIP skip. Linux/Mac app installation is not proof of local MOSS inference. No general superiority over Qwen or universal memory requirement is established.

07 / Learning from recordings

Treat adapter training as a listening experiment.

Studio exposes two different training workflows with separate compatible-runtime/GPU requirements; installing Studio on Linux/macOS does not establish training support. Neither an exported file nor a falling loss curve proves that an adapter improves a song.

PathPurpose and requirementWhere its result goes
Training screenOne reviewed region of a library recording, 8–180 seconds. Requires a compatible ComfyUI YuE2 checkpoint, audio tokenizer, training/autograd support, an idle GPU and at least 10,000 MB free VRAM according to readiness.An experimental Audio LoRA for YuE2 through ComfyUI. Separate optional native training pack; currently NVIDIA CUDA with at least 11 GB VRAM.Saved native checkpoint, then explicit Export ComfyUI LoRA. Copy/install separately, then select the compatible export in both Audio LoRA and Planner LoRA on YuE2 through ComfyUI.

A. Train a single reviewed region

  1. Use a recording you own or have appropriate permission to use. Open Training and select it from From your library.
  2. Set Start (seconds) and Region length (seconds). Use Play selected region; listen for the voice, instruments and recording quality you actually want to teach.
  3. Read the hardware report. Give the adapter a name. The 24-second, rank-8, 600-step defaults are starting settings, not a proven musical recipe.
  4. When you have agreed to spend the time, press Train this region. Keep the run ID and use Check. Training can occupy the GPU for an hour or longer; do not plan an interruptible short preview.
  5. When complete and checked, select the saved adapter on Music's compatible ComfyUI engine. Make a baseline and an adapter take with matching checkpoint, prompt, seed and generation settings. Record the adapter strength.

B. Train from a dataset in Native tools

  1. Review the optional pack size and requirements before installing it. Choose recordings and press Create dataset, or import an owned local folder.
  2. For every song, review Style, exact Lyrics and Instrumental status, then Save song. Dataset creation does not certify this metadata.
  3. Use Prepare recordings. Then select fast, balanced or thorough and press Train when ready. Optimizer, adapter and step overrides apply to custom.
  4. Inspect Saved runs. Continue a checkpoint with a higher total step target and the same dataset fingerprint. Changing metadata invalidates derived caches.
  5. Export the compatible ComfyUI LoRA, explicitly install/copy it to the shelf, then use its returned filename in the intended slots. Export does not automatically activate it in the native GGUF song engine.
  6. Evaluate with held-out prompts or recordings and a matched baseline. Keep the adapter only if the change is useful to your actual goal.

Training does not erase source terms. Check recording permissions and the model/tokenizer terms before starting. Do not advertise a measured loss decrease as voice cloning, style mastery, a licence grant or a guaranteed audible improvement.

Study exercise: describe a narrow listening question before training. Report the answer, including “no useful change heard” when that is the result.

08 / One shot

Direct a clip before directing a film.

Open Video in Full Studio. Choose an engine whose model, runtime, hardware and licence checks are satisfied. LTX provides a useful route for supported text/frame-guided shots. Other engines have different reference and audio behavior; do not assume a feature from one engine transfers to another.

Start with one subject, one action and one camera idea. “A person lifts a paper lantern at a harbour; medium shot; slow push-in; the person faces the camera” gives a clearer task than a paragraph of simultaneous action and camera movement.

  1. Choose a supported size and a short shot length. Check what the engine will actually receive: prompt, first/last frame, character reference, soundtrack or control video.
  2. Make one representative pilot with Render clip. Avoid a whole project's worth of unreviewed renders.
  3. Watch it in motion with sound. Check the opening, ending, anatomy, object count, scene geography, subject scale and camera behavior.
  4. Keep a good take. If it fails, change one variable, such as the action wording, reference, framing or seed. Record the observation.
  5. Use editing or VFX for a title, grade or transition. Render a new clip when the subject, camera or photography must change.

MiniMax H3 is a separate decision. It has model-specific territorial and other licence restrictions, plus distinct reference behavior and memory needs. Read the current Models notice for your location. Optional quantization, cache, acceleration or new PTD LoRA experiments require their own integration and validation; a newer ComfyUI or PyTorch release alone does not establish compatibility.

Study exercise: show a useful five-second pilot and one failure that taught you how to write the shot better. Label proposed settings as proposed, measured settings as measured.

09 / H3 references

Keep auto components; direct the action.

First read the current H3 licence/territory acknowledgement in Models. Install the H3 components and Video references — MiniMax H3 ref2va. App startup does not establish that this large model fits your machine.

  1. Open Video → Advanced and choose MiniMax H3.
  2. Leave Engine settings → Model file, Text encoder, Video VAE, Audio VAE on auto unless deliberately testing compatible alternatives. Automatic Turbo adapters are not custom LoRAs to add again.
  3. In References, choose Add a picture…. Name it in the prompt: <Picture 1> is Mira. Mira turns toward the window and sets down her mug. Static camera. Start with one subject and a simple action.
  4. Use a five-second pilot, supported size and saved seed. Check the displayed steps beside Standard: the labels resolve from installed files. For eight-step references, verify that it actually shows eight.
  5. Choose H3 audio → Keep it or Discard it, then Render clip. H3 generates sound either way. Watch the actual clip with sound; inspect its opening, ending and continuity.

10 / Production

Build a complete music video in stages.

A complete project is more than a collection of clips. Keep the accepted song, a clear brief, reusable references, a board for each scene, chosen takes and a reviewed export. Use Production for the plan and Studio for the cut.

  1. Upload & analyze. Create a video project with New video…, attach the accepted song and inspect the beat grid. Listen to confirm the detected pulse; half-time music can be read at double tempo.
  2. Creative interview. Decide medium, tone, narrative approach, aspect ratio, supported size and important constraints. Record them before generating assets.
  3. Script & direction. Create the story, style bible, named characters/props/locations and a storyboard for every scene. In the current interface, the first whole bible is authored by an external MCP assistant using mv_bible_spec and mv_set_bible. Once present, its parts are editable in Production. The built-in Chat currently does not expose that whole-document action.
  4. Story review. Run the free lint/review checks. Resolve missing boards and undeclared references. A scene without a board can fall back to a generic performance shot; that is rarely a useful use of your GPU.
  5. Characters & props → Backgrounds → Storyboards. Generate or import references, choose takes, and review the boards as a set. Establish identity and geography before clips. A chosen-reference change can mark dependent work stale.
  6. Video clips. Make one pilot. After it passes review, render the remaining approved scenes. Keep earlier takes and choose among them. Read stale findings before regenerating.
  7. Rough cut. Use Move to Studio to assemble the chosen scene takes with the song. Edit rhythm, trim pauses and inspect the joins. Save a separate edit before Rebuild the Studio timeline, because rebuilding replaces that project's composed timeline with the current picks.
  8. Finish & export. Add titles, grades, transitions and sound finishing. Where shown, Render the finished video composes from source clips with ffmpeg. Studio's Export video is a real-time browser canvas capture. The offline renderer combines video clips with one audio item; it does not reproduce every Studio title, layer, effect or multiple-audio mix. Check these before choosing the route. Bake finishing into source media or use a verified export route, then review the actual file. Creating a project or building a timeline does not itself produce a finished video file.
  9. Review the exported file. Play the actual result from beginning to end. Confirm sound, picture, credits, framing, cut timing and ending. Keep the project and receipts alongside the delivered version.
Read directors.md and the connected Studio's pipeline guide. Help me plan a short music video from my accepted song. Read the current project first. Write the brief and proposed scene plan, run the free review checks, and show me one concrete pilot to approve. Do not download models or render anything yet.

11 / Longer stories

Scale the planning before scaling the render queue.

A short film

Start with a logline, a beginning/turn/ending and a small scene list. Separate picture, dialogue/narration, music and effects. Keep shots short enough for the selected engine and assemble them editorially.

Production's video projects can hold the scene plan; use external planning/MCP for the first bible. Handle narration and sound as explicit assets. A text brief does not automatically produce a finished, synchronized film.

An episode or a series

Create one project per episode. Maintain a shared series bible with stable names, wardrobe, locations, props, palette and story facts.

Carry the actual chosen reference images into each project, for example with mv_import_asset. Projects do not automatically share one cast store; the same prose in two episodes does not guarantee the same face.

A production loop the group can repeat

  1. Approve the episode outline and continuity changes before asset work.
  2. Choose a representative dialogue, action or performance scene as the pilot. Prove the intended workflow with that scene first.
  3. Record accepted takes and episode-ending continuity facts. Preserve the exact reference images for the next episode.
  4. Build the cut, layer music/narration/effects, and review transitions and sound across scene boundaries.
  5. Export one review version, collect concrete notes with timecodes, and repair the smallest affected set of shots.

For a narration-led project, Production also has an audiobook workflow: ingest and select chapters, plan bundles, audition voices, assign cast, narrate, add sound cues/beds and mix. Read its own setup and source permissions. It is a useful audio spine, with visual editing still a separate production task.

Study exercise: plan a two-scene short or a second episode using the same approved character image. Share the continuity checklist before rendering.

12 / A shared working memory

Give the assistant a direction file.

Download the directors.md template and adapt it to your project. It holds the creative brief, continuity bible, shot contract, approved scope, comparison recipes and handoff log. It is a suggested project practice; AIPLAY does not automatically import it as a production bible.

Tell the agent to read it. For Codex, add that instruction to your project's AGENTS.md; for Claude Code, use CLAUDE.md. A file with this name is not automatically an instruction source in every assistant.

Before working on this creative project, read directors.md.
Read the existing Studio project and live tool schemas.
Honor the approved scope and keep the handoff log current.
Do not claim a render, listening test or export happened unless it did.

Write decisions, not wishes

Record the exact chosen reference, scene ID, take, engine and reason. Distinguish “we want a slow push-in” from “we watched this take and the camera moves correctly.”

Give the next agent a clean handoff

Keep a short latest entry: accepted constraints, current project/run IDs, what changed, what was actually watched or heard, unresolved issues and the next useful action.

Study exercise: hand the project to a fresh assistant using only your direction file and the saved Studio state. Note what it could not recover, then improve the handoff.

13 / Assistants

Connect the assistant to the running Studio.

MCP lets an outside assistant call Studio's tools. The app's Agent → MCP server card provides the configuration for your actual installation. Studio must already be running. Copy the card's actual configuration, including command, args and local URL. On Linux/Mac it points to the private Node executable supplied by the package; that runtime is not necessarily on the system PATH. Do not substitute a Windows path or assume bare node resolves. The MCP bridge is a local stdio process: node server/mcp.js; it talks to Studio's local API. The examples below show a Windows source installation with Node on PATH; the generated card is the platform-neutral choice.

This is separate from entering an API model key on Agent for the built-in Chat/Simple experience. A local MCP bridge does not require a provider key in its configuration; your chosen assistant still has its own account and data policy. Material returned to that assistant may be sent to its provider.

Codex: Windows source example

Use the current MCP configuration UI, or add the local server with the Codex CLI. Replace the placeholder path:

codex mcp add aiplay -- node "C:/YOUR/AIPLAY-Studio/server/mcp.js"
codex mcp list

In the Codex terminal interface, /mcp shows active servers. If you prefer TOML, this is a portable example for your private config.toml, not a file to publish with your machine path:

[mcp_servers.aiplay]
command = "node"
args = ["C:/YOUR/AIPLAY-Studio/server/mcp.js"]

[mcp_servers.aiplay.env]
AIPLAY_URL = "http://127.0.0.1:4173"
AIPLAY_AGENT = "codex"

Claude Code: Windows source example

Configure a local stdio server, then verify its connection:

claude mcp add --transport stdio aiplay -- node "C:/YOUR/AIPLAY-Studio/server/mcp.js"
claude mcp get aiplay
claude mcp list

Use /mcp inside Claude Code to inspect status. Claude Desktop's chat configuration is separate from Claude Code's configuration. Use Studio's generated MCP JSON for a compatible Desktop setup, and follow that client's current official instructions.

Verify with a free read first

Connect to AIPLAY and read its capabilities with showcase disabled. Read the Music screen's readiness and the music-workbench pipeline guide. Explain which engines are installed and what is missing. Do not install, download, train, render, delete or publish anything.

Useful discovery calls are studio_capabilities with showcase:false, studio_screen_info for a screen, and pipeline_guide for the task. Ask the assistant to read current schemas before using project or training tools.

If the connection fails
  1. Confirm Studio is running at the address shown by its launcher.
  2. Use the absolute Node executable from the generated Agent card, particularly on the packaged Linux/Mac install; do not replace it with bare node unless that is intentionally available to the assistant process.
  3. Confirm the script path points to your extracted installation, not a ZIP viewer or an old moved folder.
  4. If you changed Studio's port, set AIPLAY_URL in the server's environment. Leave it local.
  5. Read the client's MCP error, reconnect using that client's controls, and retry a read-only discovery call before any generation.

14 / Community practice

Share the useful part of the experiment.

Bring one clear question to each session. A failed experiment with a reproducible recipe can teach more than a polished clip without any context.

  • Show the task. Say what you wanted, the engine/model, Studio build line, main settings and the one change you tested.
  • Show evidence. Use a public-safe screenshot, short owned excerpt or actual playback. Separate your interpretation from what you watched or heard.
  • Make comparisons fair. Keep relevant settings fixed, use comparable loudness for audio, and record adapter/reference strengths.
  • Protect private material. Crop keys, paths, personal names, recent projects and unrelated library media. Obtain consent before sharing another person's voice, face or work.
  • Ask a focused question. “Does the chorus lose the words at 0:24?” is easier to answer than “Is it good?”
  • Keep the original. Save the baseline, chosen take and project before major changes. Report unsupported or unmeasured behavior honestly.

Suggested study sequence: platform setup → YuE2 songs → pictures/references → MOSS comparison → training → H3 pilot → production bible → cut/export → series handoff. Use the ready-to-copy Discord posts as invitations, not as claims that participants have completed anything.

Before public release, review the exported file, asset permissions, required attribution and the selected model's current terms. Browsing Community or building a local project does not automatically publish it. Nothing in this guide sends messages or posts files on your behalf.
